## Implementation Plan

### Background

The task has two changes:
1. Add an optional `priority` field to `ToolEntry` that overrides the inherited provider priority
2. Reformat the example `zbobr.toml` generated by the `init` command: providers and tools should be rendered in compact inline-table form

The closest analog for change 1 is `ProviderDefinition.priority: Option<i32>` — same pattern, same semantics. The dispatch logic in `zbobr-dispatcher/src/lib.rs:select_provider_excluding` groups entries by `rp.priority`; the new field would override that per-entry.

The closest analog for change 2 is the existing `inline_stage_tables()` in `zbobr/src/init.rs`, which uses `toml_edit` to post-process serialized TOML and convert tables to inline form.

---

### Change 1 — Add `priority` to `ToolEntry`

**Location:** `zbobr-api/src/config.rs` — `ToolEntry` struct

Add `priority: Option<i32>` with the same serde annotations as `ProviderDefinition.priority` (`default`, `skip_serializing_if = "Option::is_none"`). The field must also be added to the `deny_unknown_fields` struct cleanly.

**Dispatch logic update:** `zbobr-dispatcher/src/lib.rs:select_provider_excluding` — when grouping entries by priority, use `entry.priority.unwrap_or(rp.priority)` instead of `rp.priority` directly. This means a tool entry can opt into a lower (or higher) priority tier regardless of its provider's default.

**Tests:** The existing priority tests in `zbobr-dispatcher/src/lib.rs` use a `tool_entry()` helper — that helper needs the new field added (defaulting to `None`). Add at least one test that verifies a `ToolEntry` with an explicit `priority` overrides the provider's priority.

---

### Change 2 — Compact inline-table formatting in init example

**Location:** `zbobr/src/init.rs`

Two sub-changes:

**2a. Simplify providers list:** Drop `copilot_planner` from the example (align with what's shown in the task description: `copilot`, `claude`, `claude_planner`). Add one tool entry with `priority = 0` to demonstrate the new field (e.g., a "developer" tool where copilot is the fallback).

**2b. Inline-table post-processing:** Add a new `toml_edit` post-processing function (analogous to `inline_stage_tables`) that:
- Converts `dispatcher.providers` entries to inline tables (so each provider renders as `name = { executor = "..." }` under `[dispatcher.providers]`)
- Converts `dispatcher.tools` array entries to inline form (so each tool array renders as `name = [{ provider = "...", model = "..." }, ...]` under `[dispatcher.tools]`)

Both transformations follow the same `toml_edit` pattern: iterate table keys, clone as `InlineTable`, replace the item, optionally mark the parent table as dotted.

---

### No changes needed to

- The `setup_repository` function — no stage/label changes
