## Blocking issue: role/stage prompt files are resolved against the config file directory, bypassing `workflow.prompts_dir`

### Where
- `zbobr-api/src/config.rs:33-42`
- `zbobr-api/src/config.rs:72-79`
- `zbobr-api/src/config.rs:253-266`
- `zbobr-api/src/config.rs:343-356`
- `zbobr-api/src/config.rs:675-693`
- existing runtime contract:
  - `zbobr-dispatcher/src/prompts.rs:192-220`
- default config shape that relies on that contract:
  - `zbobr/src/init.rs:294-301`
  - `zbobr/src/init.rs:399-533`

### What is wrong
The new `resolve_paths()` implementations on `RoleDefinition`, `RoleDefinitionPatch`, `StageDefinition`, `StageDefinitionPatch`, and `WorkflowToml` now eagerly turn prompt file paths into paths relative to the config file directory.

But the existing runtime behavior is different:
- `prompt_files_for_stage()` explicitly treats relative prompt paths as relative to `workflow.prompts_dir` when that field is set (`zbobr-dispatcher/src/prompts.rs:194-220`)
- the generated default workflow relies on this by setting `prompts_dir = "prompts"` while roles reference prompt files like `"planner.md"`, `"worker.md"`, etc. (`zbobr/src/init.rs:411`, `428`, `476`, `533`)

With the current branch, those role/stage prompt paths become absolute under the config directory first, so they no longer get prefixed by `prompts_dir` later.

### Concrete regression
The default config generated by `zbobr init` is now effectively interpreted like this:
- expected before / by current prompt loader contract:
  - `prompts_dir = "prompts"`
  - role prompt `"planner.md"` => `<config_dir>/prompts/planner.md`
- actual after this change:
  - role prompt `"planner.md"` is resolved early to `<config_dir>/planner.md`
  - `prompt_files_for_stage()` sees an absolute path and does **not** join `prompts_dir`

So the default config and any existing config that uses `prompts_dir` plus relative role/stage prompt filenames will look for the wrong files.

### Why this is blocking
This is not just a multi-config edge case; it breaks the documented prompt-loading behavior and the repository’s own generated starter config. That makes the final path-resolution fix incorrect even though it addressed the previous “last config wins” issue.

### Suggested fix
Keep per-file anchoring, but preserve the established prompt semantics:
1. Resolve each config file’s `prompts_dir` against that file’s directory.
2. Resolve relative role/stage prompt paths against the **effective prompt base for that file**:
   - use that file’s resolved `prompts_dir` when present
   - otherwise use the config file directory
3. Do not blindly resolve role/stage prompt paths against the config file directory when `prompts_dir` exists.

That preserves both goals:
- shared configs remain anchored to their source file
- `workflow.prompts_dir` keeps working as the prompt base

### Test review
The new tests in `zbobr-api/src/config.rs` lock in the wrong behavior by asserting that role/stage prompt paths resolve directly under the config directory. Those tests should instead cover the actual runtime contract, especially the case:
- `prompts_dir = "prompts"`
- role prompt `"planner.md"`
- merged result should ultimately load from `<that config file dir>/prompts/planner.md`

## Analog consistency
The merge analog is still appropriate, and the patch-type approach for list fields is consistent with the task requirements. The remaining problem is specifically in the path-resolution layer: it diverges from the existing prompt-loading design instead of matching it.
