## Blocking issue: nested workflow prompt paths are still resolved against the config file directory, not the effective `workflow.prompts_dir`

### Where
- `zbobr-api/src/config.rs:675-693`
- nested resolvers used by that path:
  - `zbobr-api/src/config.rs:33-42`
  - `zbobr-api/src/config.rs:72-79`
  - `zbobr-api/src/config.rs:253-266`
  - `zbobr-api/src/config.rs:343-356`
- existing runtime contract:
  - `zbobr-dispatcher/src/prompts.rs:194-220`
- default config shape that depends on that contract:
  - `zbobr/src/init.rs:399-536`

### What is wrong
`WorkflowToml::resolve_paths()` currently does this:
- resolves `prompts_dir` relative to `config_dir`
- resolves role prompt paths with `role.resolve_paths(config_dir)`
- resolves pipeline/stage prompt paths with `pipeline.resolve_paths(config_dir)`

That means relative prompt files like `reviewer.md`, `review_stage.md`, or `common.md` are converted to `<config_dir>/...` immediately, instead of being rooted under the effective prompts directory when `workflow.prompts_dir` is set.

But the dispatcher still implements the longstanding contract that **relative prompt paths are prefixed with `workflow.prompts_dir`** inside `prompt_files_for_stage()`:
- `zbobr-dispatcher/src/prompts.rs:210-220`

Once the config loader has already made those paths absolute under `config_dir`, the dispatcher no longer prefixes them with `prompts_dir`, because it only prefixes relative paths.

### Concrete regression
The default workflow generated by `zbobr init` sets:
- `prompts_dir = "prompts"`
- role prompts like `"planner.md"`, `"reviewer.md"`, etc.

Expected behavior from the existing runtime contract:
- `planner.md` resolves to `<config_dir>/prompts/planner.md`

Actual behavior in the current branch:
- `planner.md` is eagerly resolved to `<config_dir>/planner.md`
- later prompt loading sees an absolute path and skips `prompts_dir`

So the generated default config and any existing config using `prompts_dir` plus relative prompt names will point at the wrong files.

### Why this is blocking
This breaks existing prompt-loading semantics, not just a new edge case. The task is about configuration sharing/overlaying; it should not change how prompt path resolution works for existing configs.

### Suggested fix
In `WorkflowToml::resolve_paths()`:
1. Resolve `prompts_dir` against `config_dir` first.
2. Compute a prompt base for nested prompt paths:
   - use resolved `prompts_dir` when present
   - otherwise fall back to `config_dir`
3. Resolve role and stage prompt fields against that prompt base, not directly against `config_dir`.

That preserves both requirements:
- each config file stays anchored to its own directory
- `workflow.prompts_dir` continues to define the base directory for relative prompt files
